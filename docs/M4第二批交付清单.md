## 四、B8 版本竞争保护（核心）

**协议**：读到正文 → 算 `source_hash` 并落库 → **事务外**做 embedding → 提交时
`UPDATE knowledge_docs SET indexed_hash=?,... WHERE id=? AND source_hash=?`；
`rowcount==0` 判定本轮过期 → **整事务回滚，一个 chunk 都不写**；`indexed_hash` 只在成功提交后前进。

**并发用例是真交错，不是顺序执行**：A 轮在独立线程中运行，嵌入替身进入时置 `Event`，主线程据此把文件改成 v2 并让 B 轮完整跑完，再放行 A。全程用 `Event` 编排，**不用 sleep 猜时序**。

**红证直接证明覆盖真实发生**（撤销条件更新后）：

```
>       assert contents == ["V2-NEW-CONTENT"]
E       AssertionError: assert ['V1-OLD-CONTENT'] == ['V2-NEW-CONTENT']
>       assert [c["content"] for c in _chunks(doc["id"])] == ["NEW-BODY"]
E       AssertionError: assert ['OLD-BODY'] == ['NEW-BODY']
```

即：无保护时旧任务确实把新版本的 chunk 正文覆盖了；有保护时落库内容为新版本且 A 轮返回 `stale=True`。

## 十一、复审阻断 B1 / B2 修复详情

### B1：旧轮次失败不得污染新版本状态

**根因**：失败路径是无条件 `UPDATE ... WHERE id=?`，绕过了 B8 的版本保护。

**修复**：

```sql
UPDATE knowledge_docs SET status='failed', last_error=?, updated_at=?
WHERE id=? AND source_hash=? AND status<>'missing'
```

`rowcount==0` → 本轮已过期，丢弃失败标记，记 `INFO index_stale_failure_discarded`，返回 `stale=True`。

**红证**（撤销条件后）：

```
E   AssertionError: assert 'failed' == 'ready'
```

即 V2 确实被旧轮次的失败标成了 failed。修复后用例断言 V2 保持 `ready`、`indexed_hash` 与 chunks 不变、`last_error is None`，且 **V2 仍可被检索到**。

**不误伤**：另有 `test_current_round_failure_still_marks_failed` 断言本轮自身失败仍正常标 failed。

### B2：旧轮次不得复活 missing 文档

**根因**：`mark_missing()` 只改 `status`，不改 `source_hash`，因此仅靠 hash 条件无法拦截。

**修复**：提交条件加 `AND status<>'missing'`。

**红证**：

```
E   AssertionError: assert 'ready' == 'missing'
```

**同源缺口（我修 B2 时一并发现并堵上）**：`TX1` 本身也是状态转换。若某轮的 TX1 晚于 `mark_missing` 执行，它会把 `status` 直接写回 `ready/processing`，随后提交条件自然通过——复活路径依旧成立。因此在 TX1 内增加判定：**当前行是 missing 且文件此刻确实不存在时，只更新归属/可见性元数据，不改状态、不重索引**，返回 `stale=True`。

这条缺口有独立红证 `red_b2_late_tx1`（`E AssertionError: assert 'ready' == 'missing'`），构造方式是在"读完文件之后、TX1 之前"用 Event 停住线程，再删文件并 `mark_missing`。

**不误伤**：`test_missing_doc_revives_when_file_reappears` 断言文件真的回来时能正常复活并重建索引。
