## 二、依赖审计（实测事实）

### 2.1 数据库现状（`opc_workbench/db.py`）

`knowledge_docs`（L340–352）实际列：

| 列 | 约束 |
|---|---|
| `id` | INTEGER PK AUTOINCREMENT |
| `filename` | TEXT NOT NULL |
| `stored_path` | TEXT NOT NULL **UNIQUE** |
| `file_hash` | TEXT NOT NULL（**无 UNIQUE**） |
| `owner_role` | TEXT NOT NULL CHECK IN `config.ROLES` |
| `visibility` | TEXT NOT NULL DEFAULT 'public' CHECK IN ('public','private') |
| `chunk_count` | INTEGER NOT NULL DEFAULT 0 |
| `status` | TEXT NOT NULL DEFAULT 'ready' CHECK IN **('processing','ready','failed','missing')** |
| `created_at` | TEXT NOT NULL |

`knowledge_chunks`（L354–361）实际列：`id / doc_id / seq / content / embedding BLOB NOT NULL`，`UNIQUE(doc_id, seq)`；索引仅 `idx_chunks_doc ON knowledge_chunks(doc_id)`（L403）。

**三条硬约束**：
1. `status` 只有四态，**加 `deleting`/`reindexing` 必须重建表**（SQLite 无法 ALTER CHECK）。
2. `knowledge_chunks` **没有 `owner_role` / `visibility` 列**，也没有模型标识与维度列。
3. `knowledge_docs` **没有 `updated_at`**，无法表达"何时最后成功索引"。

迁移机制：`MIGRATIONS = [m001_init, m002_task_idempotency, m003_report_identity_version, m004_bulk_delete_recovery]`（L536），`init_db` 经 `MigrationConnection` 受控接口执行，**禁 `executescript`**，显式 BEGIN/COMMIT/ROLLBACK。新增必须写成 `m005_*` 函数并追加进列表。

写入口：`WriteCapability`（L98）不可直构、不可变、`transaction()` 进入即 `BEGIN IMMEDIATE`，异常 ROLLBACK 后原样抛出；生产 writer 由组合根铸造并注入。**第二批所有写操作必须经注入的 writer，不得新增铸造入口。**

### 2.2 可见性治理现状（`opc_workbench/visibility.py`）

- `visible_filter`（L29）要求行含 `owner_role` 与 `visibility` 两键。
- `_QUERYABLE` 白名单（L59–65）：`tasks / schedules / knowledge_docs / memory / artifacts`。**`knowledge_chunks` 不在其中。**
- `query_visible`（L68）只支持 `SELECT * FROM <白名单表> WHERE <白名单列>=?`，**不支持 JOIN、不支持 IN、不支持自定义投影**，取回后在 Python 侧逐行 `visible_filter`。

> **这是第二批最大的结构性冲突**：向量在 `knowledge_chunks`，而该表既无治理列、也不在白名单。检索必须做可见性过滤，但现有原语无法直接查询 chunk。见 §三 C1。

### 2.3 LLM 客户端现状（`opc_workbench/llm_client.py`）

公开面：`LLMFailure` / `CircuitBreaker` / `LLMClient.chat` / `get_llm` / `set_llm`，**无 `embed`**。
可复用纪律：无 Key → `LLMFailure("no_api_key")`；熔断 `allow()` 严格单探针；`LLM_ATTEMPTS=2`、`RETRYABLE_STATUS={408,409,425,429,500,502,503,504}`、退避 `0.8*(attempt+1)`、`deadline` 越界即停。`chat` 语义**零改动**。

### 2.4 第一批 vault 接口（`opc_workbench/vault.py` @ 77c3a12）

`ROLE_DIRS`(9) / `SHARED_DIR="shared"` → `SHARED_OWNER="coordinator"` / `ATTACHMENTS_DIR` / `FM_KEYS` / `FrontmatterError` / `parse_frontmatter` / `serialize_frontmatter` / `validate_doc_meta` / `resolve_safe_path` / `owner_for_relpath` / **`load_doc`** / `atomic_write` / `diff_snapshots`。

`load_doc(root, rel, text)`（L181）内部顺序：`resolve_safe_path` → `parse_frontmatter` → `owner_for_relpath` 覆盖 → `validate_doc_meta`，返回 `{"meta","body","owner_corrected","declared_owner"}`。

**采纳你提的接口注意事项并升级为硬规则**：`load_doc` 收到的 `text` 是调用方已读入的内容，**它校验的是"路径字符串"，不是"读取行为"**。因此 ingest 的顺序必须是
`resolve_safe_path(root, rel)` → 用返回的 Path 读文件 → `load_doc(root, rel, text)`，
**禁止先读后验**。这条会写成模块 docstring 红线 + 一条断言"未校验路径不得进入 read"的测试（用会抛异常的读桩证明读取发生在校验之后）。

**审计新发现（非阻断，本批顺带修）**：`owner_for_relpath` 用 `Path(rel).parts`（L170），在 Linux 上 `cfo\a.md` 不分割 → 抛 `vault_owner_undetermined`；而 `resolve_safe_path` 已做反斜杠归一会放行。两函数对同一输入判定不一致。修法：映射前同样归一分隔符，与路径校验共用同一归一函数。

### 2.5 依赖与外部 API

锁定依赖 `requirements-personal-agent.txt` 已含 `openai 2.36.0` / `numpy 2.4.4` / `tenacity 9.1.4` / `pytest 9.0.3` → **第二批零新依赖**。

`config`：`EMBEDDING_MODEL="text-embedding-v4"`、`DASHSCOPE_BASE_URL=".../compatible-mode/v1"`、`LLM_TIMEOUT_S=30.0`、`VAULT_PATH`、`VAULT_SCAN_INTERVAL_S=30`。

`text-embedding-v4` 规格（阿里云百炼 OpenAI 兼容文档）：向量维度 2048/1536/**1024（默认）**/768/512/256/128/64；**单次请求最多 10 条文本**；**单条最多 8192 token**；兼容模式用 `dimensions` 参数指定维度。

> 与第一批分块的匹配核算：`DEFAULT_TARGET=512` 字符权重（CJK 计 1、其余 0.25），最坏情况全 CJK ≈ 512 字符，远低于 8192 token 上限，**正常路径不会触发截断**。仍会加一条"单块超长"的防御性断言。

### C1（阻断）检索的可见性通道

三种可行方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | m005 建视图 `knowledge_chunks_visible` = chunks JOIN docs，投影出 `owner_role`/`visibility`；`_QUERYABLE` 增加该视图名一行 | 需动 `visibility.py` **一行白名单**；治理列单一真源仍在 docs，无同步问题 |
| B | m005 给 chunks 增 `owner_role`/`visibility` 冗余列，chunks 进白名单 | 治理列出现第二份真相，doc 改可见性须同步 N 行 chunk，双写一致性风险 |
| C | 新增只读模块按 `query_visible("knowledge_docs")` 得到的 doc_id 白名单，用参数化 SQL 直读 chunks | 不动 M2，但**违反 CLAUDE.md「业务查询走 query_visible 禁裸 SQL」字面规则**，需你批准例外 |

推荐 A：它把 chunk 检索**接入**M2 治理而不是绕过，`visible_filter` 原样复用，boss/coordinator/自见/他见四条规则自动生效，且可见性只有一处真相。
**需你明确批准"向 `_QUERYABLE` 增加一个受控视图名"是否算修改冻结的 M2 治理原语。** 我的判断是不算（白名单是配置面，`visible_filter`/`query_visible` 逻辑零改动），但这条不该由我自行认定。

### C2（阻断）`ux_kdocs_owner_hash` 的语义

v3 设计了 `(owner_role, file_hash)` 唯一索引。实际后果：**同一角色目录下两个文件名不同但正文完全相同的文档，第二个会被拒绝入库**。
这是"内容级去重"还是误伤？两种口径：
- **去重**：保留唯一索引，第二篇入库失败并回显"内容与已有文档重复"。
- **不去重**：放弃该索引，仅靠 `stored_path UNIQUE` 防重复登记，允许同内容多文件。

我倾向**不去重**（老板把同一份材料放进 `cfo/` 两个文件名是合理行为，静默拒绝会造成"文件在但搜不到"），但这与 v3 已写的设计相反，需你裁决。

### C3（阻断）Embedding 熔断器是否与 chat 共用

共用：索引批量失败会把 chat 一起熔断，对话降级。
独立：`LLMClient` 内新增 `self.embed_breaker = CircuitBreaker()`，两条链路互不影响。
推荐**独立**。这会新增一个实例属性，不改 `chat` 任何行为。

### C4（阻断）`app.py` 接线与①分支的冲突顺序

第二批要把 `KnowledgeService` 接进组合根、并在 `main()` 启动 watcher，**必然改 `app.py`**。而 `fix/m32-writer-boundary` @ `65b042f` 也重写了 `app.py`（去 writer 槽 + `ApplicationLauncher` + `main()` 返回值变更），**该分支尚未验收合并**。

两条分支都改同一文件，先后顺序会影响冲突面。可选：
- **先合①再做第二批接线**（①仍需你验收）；
- 第二批接线**只加不改**（在现有 `build_application` 尾部追加装配、`main` 内追加 watcher 启停），把与①的语义合并留到 merge 时处理。

另需知悉：基线 `b134ac9` 的 `Application.__slots__` 仍含 `"writer"` 且仍 return，**这是已记录的未解决遗留风险**，第二批不会声称它已修复，也不会新增任何公开 writer 面。

### C5（非阻断，确认即可）Embedding 维度与模型变更策略

固定 `dimensions=1024` 并写入 `embed_model`/`embed_dim` 列；检索时**拒绝跨模型/跨维度混算**（不同维直接判不可比并跳过，记 WARN）。
模型或维度变更 → 标记受影响文档需重建索引，**不自动全量重嵌入**（避免静默产生大额 API 调用），由老板显式触发。

### C6（非阻断，确认即可）哈希口径与"元数据变更不重嵌入"

`file_hash` / `source_hash` / `indexed_hash` 统一为 **`sha256(正文 body 的 UTF-8 字节)`，不含 frontmatter**（含 frontmatter 会自指循环）。
推论：**只改 `visibility` 而正文不变时，body hash 不变 → 不触发重嵌入，但必须更新 DB 的 visibility/owner 行**。这条会单独立一个用例，否则会出现"老板把文档改成 private，向量库仍按 public 检索"的泄露。

## 五、B8 版本竞争协议（本批核心）

**要解决的问题**：A 轮索引读到 v1 正文后开始嵌入；期间文件被改成 v2，B 轮启动并完成；A 轮姗姗来迟，用 v1 的向量覆盖了 v2 的索引。

**协议**：
1. 读到正文 → 算 `source_hash` → 单事务写入 `source_hash`，并记下本轮 `expected = source_hash`。
2. 嵌入在事务外进行（网络 IO 不持写锁）。
3. 提交索引时，在**同一个事务**内：
   - 条件更新 `UPDATE knowledge_docs SET indexed_hash=?, chunk_count=?, embed_model=?, embed_dim=?, updated_at=? WHERE id=? AND source_hash=?`（参数为本轮 `expected`）；
   - **`rowcount == 0` → 判定本轮结果过期，整体 ROLLBACK，不写任何 chunk**，记 `INFO index_stale_discarded`；
   - `rowcount == 1` → 删除旧 chunk、批量插入新 chunk、COMMIT。
4. `indexed_hash` **只在成功提交后前进**；失败路径只写 `last_error` 与 `status='failed'`，`indexed_hash` 保持上一次成功值。

**不变量**：`indexed_hash` 永远对应库里实际存着的那批向量；任何时刻 chunk 内容与 `indexed_hash` 一致。

**红证要求**：这条必须先在**没有条件更新**的实现上跑出"旧覆盖新"的失败用例，再证明修复后变绿。用可编排的 `FakeLLM.embed` 阻塞点精确构造 A/B 交错，不靠 sleep。

## 六、模块与接口

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `llm_client.embed(texts, *, deadline=None)` | 生产嵌入，按 10 条分批 | 复用重试/退避/deadline 纪律；无 Key → `LLMFailure`；返回顺序与输入严格对齐（按 `index` 字段复位，不信任返回顺序） |
| `knowledge_index.py` | 向量编解码、余弦检索、维度校验 | float32 存 BLOB；L2 归一化后点积；**零新依赖**（numpy 已锁定） |
| `knowledge_service.py` | ingest / update / delete / search 状态机 | 唯一写入口是注入的 writer；读经 `query_visible`；文件读写经 vault |
| `tools/knowledge_tool.py` | 5 个 action 的 Agent 面 | `caller_role` 由框架注入经 `resolve_caller`，**禁采信 LLM 传入的身份字段** |
| `vault_watcher.py` | 周期扫描 + `diff_snapshots` 驱动增量 | 生产在 `app.main()` 启动，**不在 `build_application()` 隐式启动**；关闭须 `stop()` + `join()` |

**ingest 硬顺序**（对应 §2.4）：
`resolve_safe_path` → 读文件 → `load_doc` → 目录归属落库 → 分块 → embed → 条件提交。

**删除协议**（替代你已否决的"DB 先删→失败仅 WARN→watcher 猜孤儿"）：
写 `pending_deletions` 意图（事务）→ 删磁盘文件 → 删 DB 行与 chunk（事务）→ 删意图。任一步崩溃，重启按意图表**幂等重放**，不靠 watcher 猜测。

**失败恢复**：启动时把残留 `processing` 且无在跑任务的文档复位为 `failed` 并记原因，等待显式重试；不自动无限重试。

## 七、权限隔离（必须成立的断言）

1. `owner_role` 只来自目录映射，frontmatter 声明一律被覆盖（沿用 `load_doc`）。
2. `shared/` → `coordinator` + 强制 `public`。
3. Agent 检索结果**不含**他角色 private 文档的任何 chunk 正文。
4. coordinator 检索**看不到任何 private**，包括自己名下的。
5. boss 全可见。
6. private 正文**允许**发送到 Embedding API（PRD §28.2 已批准），但只发送当前文档所需文本块，不夹带其他文档内容；日志不落正文。
7. 老板手改 `private→public` 与 `public→private` **双向允许**（B2 裁决），改后即时生效于检索（对应 C6）。
