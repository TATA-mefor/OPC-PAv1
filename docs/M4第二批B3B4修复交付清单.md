## 一、根因确认（与复审意见一致）

**B3**：`body_hash` 按 C6 只算正文、不含 frontmatter，因此 `public→private` 这种"只改权限"的变更不改变 `source_hash`。旧轮次读到 public 后在 TX1 无条件写 `visibility`，就能把 B 已提交的 private 覆盖回 public；由于正文未变，它还会走 `already_indexed` 直接返回，形成"磁盘 private、DB public"的静默泄露。

**B4**：`delete()` 完成后 `knowledge_docs` 行与 `pending_deletions` 均已清空，B2 的 `status<>'missing'` 条件依赖的行不存在了。旧轮次读到旧正文后在 TX1 走 `row is None` 的 INSERT 分支，就能把已删除文档连同 chunks 重建出来。

## 二、B3 修复

### 2.1 方案：独立快照标识 + 写事务内复核

- 新增 `snapshot_hash(text) = sha256(原文全文 UTF-8)`，**含 frontmatter**，与 C6 的 `body_hash`（不含 frontmatter、决定是否重嵌入）**并存**：embedding 的 hash 口径没有改。
- `knowledge_docs.snapshot_hash` 记录"最近一次成功提交的权限快照"。
- **TX1 在 `BEGIN IMMEDIATE` 事务内重新读取文件并比对快照**，不一致即抛内部 `_StaleRound("snapshot_changed")`，整事务回滚：不写 visibility/owner/status，不进嵌入，不写 chunks。
- 同一快照条件同时加在**失败标记**与 **TX2 提交**上，堵住"旧轮次失败把新轮次标 failed"的 B1 × B3 交叉。

### 2.2 四种交错的实际结果

| 时序 | 结果 |
|---|---|
| A 读完 public → 文件改 private → B 完整 ingest → A 恢复 TX1 | A 重读见 private，快照不符 → stale，不写权限；DB 保持 private |
| A 读完 → 文件已改但 B 还没进 TX1 | A 的重读已能看到新内容 → stale；B 随后提交 private |
| A 的 TX1 先提交（当时文件仍是 public）→ 之后才改 private → B ingest | B 的 TX1 后提交，最终 private |
| 文件在 A 的"重读校验"与"A 提交"之间被改 | B 的 TX1 被 A 的写锁阻塞，A 提交后 B 再提交，最终仍是 private |

第四行说明了**为什么文件写盘不在写锁内也能成立**：任何写盘之后都紧跟一次 ingest（`write_doc` 自带，watcher 扫描亦如此），而该轮 ingest 的 TX1 必然排在旧轮次之后提交，因此"最后一次权限写入"一定是新快照。外部编辑器改文件但没有 ingest 时，DB 会暂时保留旧权限，这与现有语义一致，由下一轮扫描收敛。

### 2.3 顺带替换的一处旧实现（如实声明）

B2 阶段 TX1 里的 `missing_locked` 分支（"文件不在时只改归属、不改状态"）已被更强的快照校验覆盖：文件不在 → 重读失败 → 整轮 stale，**连归属/可见性都不写**。`test_late_tx1_cannot_resurrect_missing_doc` 与 `test_missing_doc_revives_when_file_reappears` 均保持通过（一绿一防误伤）。

## 三、B4 修复

### 3.1 方案：持久删除代次

- 新增表 `vault_path_state(stored_path PRIMARY KEY, generation, updated_at)`。
- `delete()` 的 `_replay_deletion` 在同一写事务内 `INSERT ... ON CONFLICT DO UPDATE SET generation=generation+1`，**先推进代次再删行**；文档行删除后墓碑保留，恢复流程（`recover()`）重放时同样推进。
- `ingest()` 在**读文件之前**取代次（`_generation_at_read`，只读连接）；**TX1 与 TX2 都在写事务内比对**，不符即 stale / rowcount=0 回滚。
- 删除后真正重新导入：新轮次读到新代次 → 正常 INSERT，新 `doc_id`，从头嵌入。

**为什么代次必须在读文件之前取**：若在读取之后取，中间发生的删除会把代次推进到新值并被本轮当成"自己的版本"，保护失效。

### 3.2 交错结果

| 时序 | 结果 |
|---|---|
| A 读完 → delete（推进代次、删行/块/文件）→ A TX1 | 代次不符 → stale，不 INSERT，无行无块 |
| A 读完 → delete → 文件被**原样字节**回写 → A TX1 | 快照相同（拦不住），**代次拦得住** → stale，仍无行 |
| A TX1 已提交 → delete → A TX2 | 行 id 已不存在 + 代次条件 → rowcount 0，整事务回滚，chunks 一个不写 |
| delete 完成后重新导入 | 新轮次取新代次 → 正常建库、可检索 |

本轮两个 schema 原语（`snapshot_hash` 列、`vault_path_state` 表）**直接并入 m005**，未新开 m006。理由：m005 属于同批未提交、未发布改动，历史库不存在；再拆一个 m006 会造成"同一批修复横跨两版 schema"的伪版本史，也会让 10 条硬编码版本断言再改一次。
