阻断：`purge_missing()` 的候选是在写事务**之外**查的，事务内不复核状态，导致"A 取到过期 missing 候选 → B 恢复文件并 ingest 成功 → A 仍按旧 id 推进代次、删 chunks、删行"，一份已恢复并重建索引的文档被过期清理永久删除。

## 2. 修复实现（`opc_workbench/knowledge_service.py`）

每条候选进入 `BEGIN IMMEDIATE` 事务后，先重查该 id 是否仍满足清理条件：

```sql
SELECT stored_path FROM knowledge_docs
WHERE id=? AND status='missing'
  AND updated_at IS NOT NULL AND updated_at<?
```

- 查不到行（已恢复、已 delete、已被前一条合并）→ 记审计 `knowledge_purge_skip_restored`（`result_code=candidate_no_longer_missing`）后跳过：不推进代次、不删 chunks、不删行。
- 查到行 → 用复核行返回的 `stored_path` 归一后推进代次、删 chunks（按旧 id）、删行。
- 复核与清理在同一个写事务内，复核通过后不存在被抢写的窗口。

返回值由 `{"purged": n}` 变为 `{"purged": n, "skipped": m}`。**这是返回结构变更**，现有调用方只读取 `["purged"]`，未见精确 dict 相等断言，但下游若有严格结构断言需同步。
