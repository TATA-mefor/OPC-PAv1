**vault 是原文真相源，SQLite 只是可重建的索引；可见性过滤在工具层强制，frontmatter 只是标记；embedding 是唯一外部调用，失败降级不击穿；全部写操作沿用 M3 写能力纪律（注入 writer，零 get_conn 写路径）。**

## 三、关键设计点（请重点审）

### 1. 可见性红线（K 组验收核心）

- search 链路顺序不可颠倒：**先按 caller 过滤 docs（query_visible）→ 再取 chunks → 再算余弦**。禁止"先全量检索后过滤"（会把 private 内容送进 numpy 计算与潜在日志）。
- chunks 无独立 visibility 列——继承所属 doc（PRD §4 口径）；doc 被过滤则其 chunks 物理不进入检索集。
- frontmatter 被手改 → **不得无条件覆盖 DB 权限**：visibility 变更必须经 `resolve_visibility()` + `validate_persist()`；owner_role 以可信目录映射为准。**按 PRD 老板手改优先，private↔public 双向均允许**（本机单用户信任假设，见 B2）；Agent/LLM 通道无改权限能力。**Agent 侧过滤永远走 DB 经 query_visible**。
- personal private 文档对 8 员工零可见（V 组红线延伸）；boss 全可见。

### 2. 幂等与原子性

- 导入幂等键 = **(owner_role, file_hash)**，由 m005 唯一索引强制（见 B4）；同键直接返回已有 doc；failed 同键重导 → **更新原行**走状态机，不新建。
- chunks 写入单事务（BEGIN IMMEDIATE，经注入 writer）；中途失败整体回滚，doc 标 failed，vault 原文保留。
- reindex = **先完成全部 embedding，再在单事务内删旧 chunks + 写新 chunks**；期间 doc 保持 `ready`、旧索引照常可检索；失败回滚，旧索引完好（见 B5）。
- delete_doc 三连带：**v1 的"DB 先删 → COMMIT → 删文件 → 失败仅 WARN → watcher 猜孤儿"方案已被审查否决**，改为删除意图表 + 重试，见 B3。

### 3. embedding 降级链

- 无 Key / 熔断 / 重试耗尽 → LLMFailure → doc 标 failed（导入）；search 时 query embed 失败 → 返回 `{"error":{"code":"llm_unavailable"}}`，**不降级为关键词搜索**（PRD 未定义该降级，不擅自加）。
- 测试全 mock（FakeLLM.embed 确定性向量）；live 用例单独标记（真实 text-embedding-v4，需 Key）。

### 4. 分块口径（PRD 512 token 的工程近似）

- 无 tokenizer 依赖（不引入 tiktoken）：按字符预算近似（中文 1 字≈1 token，英文按 4 字符≈1 token 混合估算，目标 512、重叠 64）；标题/段落边界优先切分，超长段落硬切。
- **此为显式声明的工程近似**，K 组断言块数边界与重叠语义，不断言精确 token 数。

### 5. watcher 可靠性口径（沿用 reminder best-effort 模式）

- mtime 扫描 + hash 复核（mtime 变但 hash 未变 → 跳过，防误重索引）；
- 扫描周期内多次编辑只触发一次 reindex（以扫描时点 hash 为准）；
- 进程停机期间编辑 → 启动首轮全量 hash 比对补齐；
- missing 索引保留 7 天（config 可调），超期清理 chunks + docs 行；
- 线程壳 stop_event 复查 + 异常不击穿（与 reminder 同款测试）。

### 6. 写能力纪律（M3 裁决延续）

- ingest/reindex/delete/report 双写登记全部经组合根注入 writer；**零 get_conn 写路径**（哨兵测试沿用）。
- vault 文件写不经 WriteCapability（文件系统不是 SQLite）——路径安全由 vault.py 强制（resolve 后必须在根内）。
- watcher 线程持有注入 writer 引用（与 reminder 同款），不自行取连接。

### B2. frontmatter 可见性修改（**审查裁决：按 PRD 老板手改优先，v2 的"一律拒绝"已作废**）

**信任假设（显式声明）**：本项目威胁模型是**本机单用户**（PRD §10.3），不做 OS 级文件权限隔离。文件系统无法证明操作者身份；**老板本人管理 vault，直接编辑文件视为老板的显式指令**，这是项目已确定的信任假设，不是密码学身份认证。

链路仍为 **解析 → 规则校验 → 受限更新**，禁止裸 `UPDATE knowledge_docs SET visibility=<frontmatter值>`。

- **visibility 必须经 `resolve_visibility()` + `validate_persist()`** 后才写 DB。
- **`private→public` 允许**按老板显式修改更新 DB；**`public→private` 同样允许**，立即收紧。
- **owner_role 唯一来源 = vault 目录映射**（10 角色目录 + `shared/`→coordinator）。frontmatter 的 owner_role 与目录不符 → **以目录为准**，记 WARN + 回显，**不得伪造其他角色归属**。
- **Agent / LLM Function Calling 不得借此修改权限**：文件编辑通道与工具通道分离，工具侧无 set_visibility 能力。
- **DB 仍是 Agent 查询时唯一的可见性判断依据**，一律经 `query_visible`。
- **fail closed**：缺字段 / 非法值 / 重复键 / 未知键 / 类型错配 / 畸形分隔符 → doc `status=failed`，不进 search，vault 原文保留。

### B3. 删除意图 + 重试（替代 DB 先删）

**m005 新表**：`pending_deletions(doc_id PK, stored_path, owner_role, created_at)`。

1. **事务 A**：`INSERT pending_deletions` + `UPDATE knowledge_docs SET status='missing'` → COMMIT。
   （复用既有四态，避免为加 `deleting` 而重建表；search 只取 `ready`，故此刻立即不可见）
2. 删除 vault 文件。
3. 成功 → **事务 B**：`DELETE chunks` + `DELETE docs` + `DELETE pending_deletions` → COMMIT。
4. 失败 → **保留删除意图**，返回 `{deleted:true, pending_file:true}`；watcher 下轮重试第 2 步。

**watcher 对未登记文件的判定顺序（关键）**：先查 `pending_deletions.stored_path` → 命中 = **删除重试，绝不导入**；未命中 = 新增文件。两类永不混淆。
**崩溃恢复**：启动首轮先重试全部 `pending_deletions`，再做新增扫描。
**幂等**：文件已不存在视为删除成功，不报错。

**report 双写同款恢复**：`pending_vault_writes(artifact_id PK, vault_path, owner_role, visibility, created_at)`；写失败入表，watcher 重试，成功后删表行。**不是只记 WARN**。

### B4. 幂等键作用域与并发闭环

- **幂等键 = `(owner_role, file_hash)`**。理由：同一文件被两个角色导入应各自独立 doc、各自可见性，避免跨角色串线；`stored_path` 已 UNIQUE 且含角色目录，二者天然一致。
- **m005**：`CREATE UNIQUE INDEX ux_kdocs_owner_hash ON knowledge_docs(owner_role, file_hash)`。
- **迁移前置检查**：既有行若存在同键重复 → 迁移 **fail fast 抛明确错误**，不静默删数据。
- **并发**：不靠"先 SELECT 再 INSERT"。用 `INSERT ... ON CONFLICT(owner_role,file_hash)` + `RETURNING` 取 doc_id，且全程在 writer 的 `BEGIN IMMEDIATE` 内串行。
- **状态机（复用四态，不新增状态）**：

```
new    → processing → ready
                    ↘ failed
failed → processing → ready / failed      （更新原行，不新建）
ready  → ready                             （reindex 期间保持 ready，旧索引不动，成功后原子替换 chunks）
ready  → missing → 物理删除                （文件被删 或 删除意图）
```

- **移动目录**：身份是 `(owner, hash)`，`stored_path` 只是属性 → 更新路径，不新建 doc。

### B5. watcher 删除 / 重建 / 重入语义

**四层拆分（采纳审查意见，纯函数不做 IO）**：

1. `snapshot_vault()` —— 文件系统 IO，产出 `{path: (mtime, size)}` 快照
2. `diff_snapshots(a, b)` —— **纯函数**比较，产出候选变更集
3. `apply_changes()` —— 读内容 + 算 hash + 事务处理
4. `watcher_loop()` —— 线程壳，stop_event 复查、异常不击穿

- **missing 不进 search**：search 一律 `WHERE status='ready'`。
- **单次处理绑定快照**：apply 时**只读一次文件字节**，hash 与 embedding 全部基于该字节串，**不再二次读文件**。
- **防旧覆盖新**：写 chunks 前在**同一事务内**核对 DB 当前 `file_hash` 是否等于本次快照 hash；不等 → 放弃写入并回滚，保留旧索引，下轮重处理。
- **reindex 失败保留旧索引**：先完成全部 embedding，再单事务原子替换；绝不先删旧 chunks。
- **重复发现去重**：以 `(doc_id, file_hash)` 为在途处理键，同键不重复启动。
- **停机恢复**：启动首轮全量 hash 比对 + 两张 pending 表重试。
- **启停**：交付 `start()` / `stop()` 原语，stop 设 event 并 **join 等待线程退出**；生产在 `app.main()` 调用，**不在 `build_application()` 构造时隐式启动**。

> ✅ **审查已批准（2026-11-22）**：允许 private 文档正文参与外部 embedding，依据 PRD §28.2（向量化可能将相关片段含 private 数据发送至 DashScope）。**不改成"仅 public 建索引"**。
>
> **实施约束（必须遵守）**：
> 1. 只发送**当前文档需要向量化的文本块**；
> 2. 不发送无关文档、密钥或额外业务上下文；
> 3. **日志不记录原始文本与 embedding 请求正文**；
> 4. private 文档仍遵守原有角色可见性过滤（本地存储与外部处理是两回事）；
> 5. 产品说明须如实表达此外发行为。

**向量存储契约**：

| 项 | 规定 |
|---|---|
| dtype / 序列化 | `float32` 小端 `<f4`；`numpy.tobytes()` 入 BLOB，`np.frombuffer(blob, dtype='<f4')` 读出 |
| 维度 | **不硬编码**。首批返回后取实际维度写入 `knowledge_docs.embed_dim`；后续批次维度不符 → fail closed |
| 模型标识 | `knowledge_docs.embed_model` 记录产出该 doc 向量的模型名 |
| 归一化 | 入库前 L2 归一化；检索用点积等价余弦 |
| NaN / Inf / 零向量 | 拒绝该批 → doc `failed`，不入库 |
| 维度不一致 | query 向量与候选 doc 的 `(embed_model, embed_dim)` 必须一致；不一致的 doc **排除出检索集**，不参与计算 |
| 模型升级 | 旧向量视为 stale，待 reindex 重建；**不同模型的向量绝不混入同一检索集合** |

**m005 增列**：`ALTER TABLE knowledge_docs ADD COLUMN embed_model TEXT NOT NULL DEFAULT ''`、`ADD COLUMN embed_dim INTEGER NOT NULL DEFAULT 0`（ADD COLUMN 无需重建表）。

### B8. reindex 版本竞争语义（**第二批前必须冻结**）

v2 只写"写前核对 DB 当前 file_hash"，但未定义 `file_hash` 何时更新——若不更新则永远不匹配，若开始就更新则一个字段同时表示"当前文件"与"旧索引版本"，语义混淆。

**修订：拆成两个版本字段**

| 字段 | 含义 | 更新时机 |
|---|---|---|
| `source_hash` | 最新观察到的文件内容版本 | watcher 观察到新内容时立即更新 |
| `indexed_hash` | **当前 chunks 实际对应**的文件版本 | 仅在新 chunks 原子替换成功的同一事务内更新 |

**提交条件**：本次处理任务携带启动时读到的 `source_hash` 快照；写 chunks 的事务内比较 `任务快照 == DB 当前 source_hash`，**相等才提交**并同时把 `indexed_hash` 置为该值；不等则回滚放弃，旧索引（`indexed_hash` 对应的 chunks）继续可用，下轮以新 `source_hash` 重做。

**流程**：旧索引继续可用 → 新 embedding 完成 → 版本校验 → 原子替换。

**m005 相应增列**：`source_hash TEXT NOT NULL DEFAULT ''`、`indexed_hash TEXT NOT NULL DEFAULT ''`（既有 `file_hash` 保留为导入幂等键，不参与竞争判定）。

**必须覆盖的测试**：旧 embedding 尚未完成时 watcher 已观察到新版本 → **旧任务不得覆盖新版本**；reindex 失败后 `indexed_hash` 与旧 chunks 保持一致且可检索。
